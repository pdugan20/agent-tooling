# Formal Spec

1. Inspect the relevant product and repository context before specifying behavior.
2. Separate confirmed decisions from assumptions and unresolved questions.
3. Resolve only questions that materially change scope; keep minor implementation choices open.
4. Define user-visible behavior, boundaries, data or state changes, failure cases, and platform constraints.
5. Write concrete acceptance criteria without prescribing unnecessary implementation detail.
6. Keep the result concise and proportional to the change.

Do not create a spec file, branch, plan, or commit unless asked. Do not restart ideation when a direction is already chosen.
